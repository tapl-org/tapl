\medskip\noindent
Oymomo is an extension of the untyped $\lambda$-calculus: to variables, abstraction and
application it adds structs, projection and byte arrays, which name
opcodes; its $\beta$ rule is call-by-value, so a run-time operation is never copied. Section~\ref{sec:syntax} gives the syntax, Sections~\ref{sec:computation}
and~\ref{sec:congruence} the reduction (full $\beta$), Section~\ref{sec:runs} what runs at compile time
and at run time, Section~\ref{sec:modules} how a program maps to LLVM, and Section~\ref{sec:strategy} the
order the compiler reduces in.




%% ── Syntax ─────────────────────────────────────────────────────────────

\section{Syntax}\label{sec:syntax}

\[
\begin{array}{l@{\quad}rcll}
 & t & ::= & & \textit{term} \\
\pt &   & \mid & x & \textit{variable} \\
\pt &   & \mid & \lam{x}{t} & \textit{abstraction} \\
\pt &   & \mid & t\ t & \textit{application} \\
\pt &   & \mid & \{l_i = t_i\}_{i<k} & \textit{struct} \\
\pt &   & \mid & t.l & \textit{projection} \\
\pt &   & \mid & b & \textit{byte array} \\[6pt]
\pt & v & ::= & \lam{x}{t} \mid \{l_i = v_i\}_{i<k} \mid b &
  \textit{value} \\
\pt & d & ::= & b \mid \{l_i = d_i\}_{i<k} &
  \textit{data} \\
\pt & u & ::= & v \mid x.l_1 \cdots l_n \quad (0 \le n) &
  \textit{copyable}
\end{array}
\]
\begin{points}
\item $x$ ranges over variables, $l$ over labels, $b$ over byte
  arrays and $t$ over
  terms; $u$ over copyable terms, the values and the paths $x.l_1\cdots l_n$ (row 9), which
  \rn{E-Beta} may copy. Subscripts ($t_1$, $t_2$, \dots) mark different terms in one
  rule.
\item A lambda $\lam{x}{t}$ extends as far right as possible:
  $\lam{x}{\lam{y}{t}}$ is $\lam{x}{(\lam{y}{t})}$. The dot right after the binder ends the binder; every other
  dot is projection: $\lam{p}{p.a}$ is $\lam{p}{(p.a)}$.
\item A byte array $b$ is a sequence of bytes.
  \begin{subpoints}
  \item Where a number is expected, $b$ is read as an unsigned, little-endian
    number: $\hex{0201}$ is $258$, and the empty byte array is $0$.
  \item It is mostly written in hex, $\hex{01ff}$.
  \item When its bytes are valid UTF-8 text, it may be written as text
    instead: $\str{i32}$ is the byte array $\hex{693332}$.
  \end{subpoints}
\item Types are not a separate syntax: a type is an ordinary term, passed to an opcode as an operand: $\str{add}\ \{\str{i32}, a, b\}$ is LLVM's
  $\kw{add\ i32}\ a, b$. Oymomo has no type checking: no rule looks at a type,
  so it can be seen as an untyped $\lambda$-calculus. A type matters only to the
  opcode that receives it, and to LLVM.
\item A struct's fields are ordered.
  \begin{subpoints}
  \item $\{l_i = t_i\}_{i<k}$ has $k$ fields, $l_0 = t_0$ up to $l_{k-1} = t_{k-1}$; with
    $k = 0$ it is the empty struct $\{\}$.
  \item A label may be empty (no label); the other labels are unique.
  \item A struct is consumed by projection, by opcodes, and by a byte array:
    applied to one, it selects a field (1/16, 1/18).
  \end{subpoints}
\item A byte array applied to a struct, $b\ \{l_i = t_i\}_{i<k}$, is an
  opcode call: $b$ names the opcode and the struct holds its operands, as in
  $\str{add}\ \{\str{i32}, a, b\}$.
  \begin{subpoints}
  \item $\fn{op}(b)$ is a partial function from operand values to a byte array.
    It is undefined for an effect, for undefined behavior (division by zero) and
    for an opcode it doesn't know, so reduction cannot reduce such a call.
  \item Effects include printing and every memory opcode: $\str{alloca}$,
    $\str{load}$ and $\str{store}$.
  \item Reduction has no memory: it never computes an address or the contents of
    one; the program orders memory opcodes with $\kw{let}$s (1/19) or by using
    one's result in the next (4/3).
  \end{subpoints}
\item Positions count every field, labeled or not, from $0$; a label is a
  name for one position.
  \begin{subpoints}
  \item A struct applied to a byte array $b$ selects the field at position $b$;
    past the last field it selects the last one, so the last field is a default arm.
  \item In $s = \{x = a, b, y = c\}$: $s\ \hex{00} = s.x = a$, $s\ \hex{01} = b$,
    $s\ \hex{02} = s.y = c$. An unlabeled field is reached only by its position.
  \item With a constant byte array, selection and projection both become LLVM's
    $\kw{extractvalue}$ with a constant index.
  \end{subpoints}
\item A struct is a value only when all its fields are values. Its fields are computed
  in no particular order: full $\beta$ may step any of them.
\item A branch is a struct applied to a byte array known only at run time.
  \begin{subpoints}
  \item $\{\mathit{false} = t_2, \mathit{true} = t_1\}\ c$ takes $t_1$ when $c$ is
    not $0$ and $t_2$ when it is $0$, as LLVM's $\kw{br\ i1}$.
  \item With more fields it is a multi-way branch, as LLVM's $\kw{switch}$.
  \item The labels only document the arms.
  \end{subpoints}
\item Sugar for $\kw{let}$: $\kw{let}\ x = t_1\ \kw{in}\ t_2$ is $(\lam{x}{t_2})\ t_1$.
  \begin{subpoints}
  \item When $t_1$ reduces to a copyable term, \rn{E-Beta} copies
    it to every use of $x$ (or drops it).
  \item Otherwise, as for a run-time operation, the $\kw{let}$ stays: $t_1$ runs
    once, first, and $x$ names its result.
  \end{subpoints}
\item Sugar: $\kw{if}\ c\ \kw{then}\ t_1\ \kw{else}\ t_2$ is $\{t_2, t_1\}\ c$.
\item Terms are equal up to $\alpha$-equivalence (renaming bound variables).
  When a bound variable of $t_1$ clashes with a free variable of $t_2$,
  $\subst{x}{t_2}{t_1}$ first renames it ($\alpha$-conversion), then
  substitutes.
\item A stuck term is one no rule will ever reduce:
  \begin{subpoints}
  \item a struct applied to a value that is not a byte array;
  \item the empty struct applied to anything;
  \item a byte array applied to a value that is not a struct;
  \item an opcode call whose operand is a value that is not data (a lambda
    somewhere in it);
  \item $v.l$ where $v$ is a lambda, a byte array or a struct with no field $l$.
  \end{subpoints}
\item A program whose normal form contains a stuck term, anywhere, is rejected at
  compile time. An unknown opcode or undefined behavior is not stuck: it is a
  run-time operation (1/15). A normal form that is not in the shape LLVM needs
  (Section~\ref{sec:modules}) is rejected too, such as an operand that is a run-time operation:
  $\str{add}\ \{\str{i32}, \str{mul}\ \{\dots\}, x\}$; it is written with a $\kw{let}$ instead.
\end{points}

%% ── Computation ────────────────────────────────────────────────────────

\section{Computation (at the root)}\label{sec:computation}

\begin{rules}
\axiomrow{E-Beta}
  {(\lam{x}{t_1})\ u \;\step\; \subst{x}{u}{t_1}}
\rulerow{E-Proj}
  {l_j = l}
  {\{l_i = t_i\}_{i<k}.l \;\step\; t_j}
\rulerow{E-Index}
  {b < k}
  {\{l_i = t_i\}_{i<k}\ b \;\step\; t_b}
\rulerow{E-Default}
  {0 < k \le b}
  {\{l_i = t_i\}_{i<k}\ b \;\step\; t_{k-1}}
\rulerow{E-Opcode}
  {\fn{op}(b)(d_i)_{i<k} = b'}
  {b\ \{l_i = d_i\}_{i<k} \;\step\; b'}
\end{rules}
\begin{points}
\item A value is $\lam{x}{t}$, a struct of values or a byte array (Section~\ref{sec:syntax}).
  \rn{E-Beta} substitutes only a copyable argument (row 1/9): $(\lam{x}{t})\ (\str{print}\ \{\str{h}\})$
  is not a redex, so the $\kw{print}$ is never copied or dropped; it stays a $\kw{let}$ (1/19).
\item \rn{E-Proj} takes the field labeled $l$ (labels are unique), and \rn{E-Index}
  the field at position $b$~(\rn{E-Default} the last field).
  \begin{subpoints}
  \item The other fields are discarded, even one with an effect:
    $\{a = e, b = \hex{01}\}.b \step \hex{01}$. Full $\beta$ may
    reduce $e$ or not, but $e$ is not in the normal form: it is dropped.
  \item To run it, bind it first with a $\kw{let}$:
    $(\lam{x}{\{a = x, b = \hex{01}\}.b})\ e$.
  \end{subpoints}
\item So a branch whose condition is known at compile time
  keeps one arm and discards the others. Full $\beta$
  may reduce a discarded arm or not, but it does not contribute to the normal form.
\item \rn{E-Opcode} computes the call at compile time, when $\fn{op}(b)$ is
  defined: \[\str{add}\ \{\str{i32}, \hex{02000000}, \hex{03000000}\} \step \hex{05000000}\]
  \begin{subpoints}
  \item All operands are data: byte arrays, or structs of data (row 8), never
    a lambda, so they never step and the result is the same in every reduction order.
  \item Otherwise reduction cannot reduce the call: it is a run-time operation: an effect, undefined behavior, or an operand not known until run
    time. The translation to LLVM emits it as an instruction.
  \item Operands are computed by \rn{E-App2} and \rn{E-Struct}.
  \end{subpoints}
\end{points}

%% ── Congruence ─────────────────────────────────────────────────────────

\section{Full \texorpdfstring{$\beta$}{beta}}\label{sec:congruence}

\begin{rules}
\rulerow{E-Abs}{t \step t'}{\lam{x}{t} \;\step\; \lam{x}{t'}}
\rulerow{E-App1}{t_1 \step t_1'}{t_1\ t_2 \;\step\; t_1'\ t_2}
\rulerow{E-App2}{t_2 \step t_2'}{t_1\ t_2 \;\step\; t_1\ t_2'}
\rulerow{E-Struct}{t_i \step t_i'}
  {\{\dots, l_i = t_i, \dots\} \;\step\; \{\dots, l_i = t_i', \dots\}}
\rulerow{E-Proj1}{t \step t'}{t.l \;\step\; t'.l}
\end{rules}
\begin{points}
\item $\step$ is full $\beta$: a rule of Section~\ref{sec:computation} may fire
  anywhere, under a lambda, in a struct field (so in every arm of a branch) too.
\item $\step$ is confluent: it is the call-by-value $\lambda$-calculus (Plotkin's $\lambda_v$) with
   structs, projection and branching (Church--Rosser; projection is the usual record rule). The
  proof is in Lean 4, in \texttt{proofs/} (theorem \texttt{Oymomo.confluence}), for
  every opcode table $\fn{op}$; it is still for the previous rules (full $\beta$ and strict
  application) and is being updated.
\end{points}

%% ── Meaning ────────────────────────────────────────────────────────────

\section{What Runs}\label{sec:runs}

\begin{points}
\item At compile time, reduction never runs an effect: an effectful operation (an opcode call reduction cannot reduce, 2/9) is left as it is at compile time. Full $\beta$ may copy or discard a term
  freely; since it is confluent, every order reaches the same normal form.
\item At run time an effect runs as a step: $p = \kw{print}\ \str{h}$ steps to its
  result $r$ and writes $\str{h}$. Any order of steps is allowed, so one program may
  write different output on different paths, even though every path reaches the same
  normal form, which does not show the output. For example, $(\lam{x}{\{x, x\}})\ p$:
  \begin{subpoints}
  \item $(\lam{x}{\{x, x\}})\ p \step (\lam{x}{\{x, x\}})\ r$, writing $\str{h}$,
    then $\step \{r, r\}$: the output is $\str{h}$;
  \item $(\lam{x}{\{x, x\}})\ p \step \{p, p\}$, then each $p$ runs:
    $\{r, r\}$ again, but the output is $\str{hh}$.
  \end{subpoints}
\item To run an effect exactly once, use a strict application:
  $(\lam{x}{\{x, x\}})\ {!}p$ waits until $p$ is a value, so only path 4/2(1) is
  possible, and the output is $\str{h}$. Effects run in the order the program asks for,
  with a strict application or by using one effect's result in another; any other
  order, and how many times a copied effect runs, is free.
\item So the translation to LLVM may follow any path (it follows Section~\ref{sec:strategy}): it runs an effect under a strict
  application exactly once, and a copied effect once or once per copy. For example, with $p = \kw{print}\ \str{h}$ and
  $q = \kw{add}\ \{\str{i32}, a, b\}$ (pure):
  \begin{subpoints}
  \item $\{p, p\}$ may become one or two $\kw{print}$ instructions;
  \item $\{q, q\}$ may become one $\kw{add}$ instruction whose result fills both
    fields;
  \item $(\lam{x}{\{x, x\}})\ {!}p$ becomes one $\kw{print}$ instruction whose
    result fills both fields.
  \end{subpoints}
\end{points}

\section{Modules}\label{sec:modules}

\begin{points}
\item A module is $\lam{m}{\{l_i = t_i\}_{i<k}}$: a struct of labeled
  definitions, declarations, constants and global variables. Each label is a global name, as LLVM's
  $\kw{@gcd}$ or $\kw{@puts}$. They refer to each other through $m$.
\item A definition is a struct
  $\{\mathit{gives} = t',\
  \mathit{body} = \lam{f}{\{l_i = t_i'\}_{i<k}}\}$, with $0 < k$ blocks. It becomes
  LLVM's $\kw{define}$.
  \begin{subpoints}
  \item $\mathit{gives}$ is the result type; types are ordinary terms (1/13).
  \item The parameters and their types are those of the first block, at position $0$.
  \item $\mathit{body}$ is a recursive function: $f$ names its own struct of blocks.
  \end{subpoints}
\item A block is a struct $\{\mathit{takes} = \{x_i = t_i\}_{i<k},\
  \mathit{body} = \lam{p}{t}\}$.
  \begin{subpoints}
  \item $\mathit{takes}$ declares the types of the block parameters (LLVM's
    $\kw{phi}$).
  \item $\mathit{body}$ takes one argument, a struct of the same form as
    $\mathit{takes}$: $\{x_i = t_i'\}_{i<k}$; $t$ reads it as $p.x_i$.
  \item The first block (position $0$) runs first: the translation takes the first
    field as the entry, so any label works there ($\mathit{entry}$ in 5/9). No block jumps to it, as LLVM's entry block has no predecessors. Full
    $\beta$ may still reach it, by its label or by position;
    only the translation to LLVM rejects such a jump.
  \item A jump is $f.l.\mathit{body}\ \{x_i = t_i'\}_{i<k}$, LLVM's $\kw{br}$.
  \item A block sees only its own argument, $f$ and $m$.
  \end{subpoints}
\item A declaration is a struct $\{\mathit{takes} = \{x_i = t_i\}_{i<k},\ \mathit{gives} = t'\}$,
  a function defined outside the module; $\mathit{takes}$ holds the parameter
  types in order: $\{\mathit{takes} = \{s = \str{ptr}\},\ \mathit{gives} = \str{i32}\}$
  becomes LLVM's $\kw{declare\ i32\ @puts(ptr)}$.
\item A constant is a struct $\{\mathit{type} = t_1,\ \mathit{value} = v\}$:
  $\{\mathit{type} = \str{i32},\ \mathit{value} = \hex{2a000000}\}$ becomes LLVM's
  $\kw{@answer\ =\ constant\ i32\ 42}$. $m.l$ stands for the value $v$.
\item A global variable is a struct $\{\mathit{type} = t_1,\ \mathit{init} = v\}$:
  $\{\mathit{type} = \str{i32},\ \mathit{init} = \hex{29000000}\}$ becomes LLVM's
  $\kw{@counter\ =\ global\ i32\ 41}$. $m.l$ stands for its address, a
  $\str{ptr}$; the program reads and writes it with $\str{load}$ and
  $\str{store}$.
\item $m.l$ stands for the function $l$ itself, so a call is a plain
  application to one struct: $m.l\ \{x_i = t_i'\}_{i<k}$, LLVM's $\kw{call}$. For a definition, $m.l$
  is the $\mathit{body}$ of its first block with $f$ tied to its own
  struct of blocks.
\item $m$ and $f$ stay free variables, so calls and jumps don't reduce at compile time.
  \begin{subpoints}
  \item Reduction never unfolds them, and a recursive function or a loop doesn't
    make reduction loop.
  \item The user may replace them (with a fixed-point combinator) to compute calls
    at compile time; a call to a declaration stays stuck: it has no $\mathit{body}$.
  \end{subpoints}
\item For example, Euclid's $\gcd$, with the sugars of 1/19 and 1/20:
  \begin{Verbatim}[commandchars=\@\<\>, xleftmargin=2em]
@vlamm.@ {
  gcd = {gives = 'i32', body = @vlamf.@ {
      entry = {takes = {a = 'i32', b = 'i32'}, body = @vlamp.
        f.loop.body {a = p.a, b = p.b}
      },
      loop = {takes = {a = 'i32', b = 'i32'}, body = @vlamp.
        let z = 'icmp_eq' {'i32', p.b, [00000000]} in
        if z then
          f.done.body {a = p.a}
        else
          f.step.body {a = p.a, b = p.b}
      },
      step = {takes = {a = 'i32', b = 'i32'}, body = @vlamp.
        let r = 'urem' {'i32', p.a, p.b} in
        f.loop.body {a = p.b, b = r}
      },
      done = {takes = {a = 'i32'}, body = @vlamp.
        p.a
      }
    }
  },
  main = {gives = 'i32', body = @vlamf.@ {
      entry = {takes = {}, body = @vlamp.
        m.gcd {a = [30000000], b = [12000000]}
      }
    }
  }
}
\end{Verbatim}
\end{points}

%% ── Strategy ─────────────────────────────────────────────────────────

\section{Strategy}\label{sec:strategy}

Sharing normal order, $\stepS$, is the order the compiler reduces in.
It uses three more forms:
\[
\begin{array}{l@{\qquad}l@{\qquad}l}
\pt & u ::= v \mid x & \textit{copyable} \\
\pt & (\lam{x}{t_1})\ t_2 \quad t_2 \notin u & \textit{shared } \kw{let} \\
\pt & w: \text{ a term in which every redex is a shared } \kw{let} & \textit{shared normal form}
\end{array}
\]
Each row below matches a shape and chooses either a rule of Section~\ref{sec:computation}, which fires at the root, or a part of the term, which takes its own $\stepS$ step.

\[
\begin{array}{l@{\qquad}l@{\qquad}l}
& \textit{shape} & \textit{choose} \\ \hline
\pt & (\lam{x}{t_1})\ u & \rn{E-Beta} \\
\pt & (\lam{x}{t_1})\ w & t_1 \\
\pt & (\lam{x}{t_1})\ t_2 & t_2 \\
\pt & t\ {!}v & \rn{E-Strict} \\
\pt & t_1\ {!}w & t_1 \\
\pt & t_1\ {!}t_2 & t_2 \\
\pt & \{l_i = t_i\}_{i<k}.l \quad l_j = l & \rn{E-Proj} \\
\pt & t.l & t \\
\pt & \{l_i = t_i\}_{i<k}\ b \quad b < k & \rn{E-Index} \\
\pt & \{l_i = t_i\}_{i<k}\ b \quad 0 < k \le b & \rn{E-Default} \\
\pt & b\ \{l_i = d_i\}_{i<k} \quad \fn{op}(b)(d_i)_{i<k} = b' & \rn{E-Opcode} \\
\pt & \{l_i = t_i\}_{i<k}\ w & \{l_i = t_i\}_{i<k} \\
\pt & \{l_i = t_i\}_{i<k}\ t_2 & t_2 \\
\pt & w\ t_2 & t_2 \\
\pt & t_1\ t_2 & t_1 \\
\pt & \lam{x}{t} & t \\
\pt & \{l_i = t_i\}_{i<k} \quad t_j \notin w,\ t_i \in w \text{ for } i < j & t_j \\
\end{array}
\]
\begin{points}
\item Rows are tried top to bottom; the first whose shape matches chooses. A chosen part
  steps by $\stepS$, and the rule of Section~\ref{sec:congruence} for its position (for
  example \rn{E-App2} for $t_2$ in $t_1\ t_2$) carries the step to the whole term. A term in $w$ has
  no $\stepS$ step: no row chooses it, or the chosen part is in $w$. Every other term has one.
\item A shared $\kw{let}$ (row 2) holds, for example, a run-time operation. It is not contracted: $t_2$ steps until it is in $w$, then $t$ (rows 4 to 6).
  \begin{subpoints}
  \item Keeping the $\kw{let}$ may leave a projection or an index on $x$; it stays as an instruction.
  \item $t_2$ is not copied: it runs once, as in path 4/2(1).
  \end{subpoints}
\item Outermost first (rows 12, 13 and 16 before row 15), so a branch whose condition is known fires before its arms, and
  a discarded arm is never reduced. With a run-time condition, each arm is reduced.
\item For a term in $w$ (row 3), substituting its shared $\kw{let}$s and reducing on gives its normal form under $\step$ (3/7).
\item The shared normal form of a block's body is a chain of $\kw{let}$s ending in a jump,
  a branch or a result. The translation to LLVM emits each $\kw{let}$ as one instruction.
  \begin{subpoints}
  \item A shared $\kw{let}$ of a branch whose arms are data, variables or fields of a
    variable ($d$, $x$ or $x.l$), $\{l_i = t_i\}_{i<k}\ t$, is
    emitted as LLVM's $\kw{select}$ (a chain of them when $2 < k$):
    $\kw{let}\ r = \kw{if}\ z\ \kw{then}\ p.a\ \kw{else}\ [02]\ \kw{in}\ t$.
  \item A shared $\kw{let}$ of any other branch, such as a branch of jumps, is rejected at
    compile time; the branch is written as the block's end instead.
  \end{subpoints}
\item $\stepS$ is deterministic, and each of its steps is a $\step$ step. If a term has a
  normal form, $\stepS$ is expected to reach its shared normal form (not proved yet).
\end{points}
