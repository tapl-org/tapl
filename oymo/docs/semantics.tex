\section{Syntax}\label{sec:syntax}

\[
\begin{array}{l@{\quad}rcll}
 & t & ::= & & \textit{term} \\
\pt &   & \mid & x & \textit{variable} \\
\pt &   & \mid & \lam{x}{t} & \textit{lambda} \\
\pt &   & \mid & t\ t & \textit{application} \\
\pt &   & \mid & t\ {!}t & \textit{strict application} \\
\pt &   & \mid & \{l_1 = t_1, \dots, l_n = t_n\} & \textit{struct} \\
\pt &   & \mid & t.l & \textit{projection} \\
\pt &   & \mid & b & \textit{byte array} \\[6pt]
\pt & v & ::= & \lam{x}{t} \mid \{l_1 = v_1, \dots, l_n = v_n\} \mid b &
  \textit{value} \\
\pt & d & ::= & b \mid \{l_1 = d_1, \dots, l_n = d_n\} &
  \textit{data}
\end{array}
\]
\begin{points}
\item $x$ ranges over variables, $l$ over labels, $b$ over byte
  arrays and $t$ over
  terms. Subscripts ($t_1$, $t_2$, \dots) mark different terms in one
  rule. A lambda $x \to t$ extends as far right as possible:
  $x \to y \to t$ is $x \to (y \to t)$.
\item A byte array $b$ is a sequence of bytes. Where a number is
  expected, $b$ is read as an unsigned, little-endian number: $\hex{0201}$ is $258$, and the empty byte array is $0$. It is mostly written in hex,
  $\hex{01ff}$. When its bytes are valid UTF-8 text, it may be written as text
  instead: $\str{i32}$ is the byte array $\hex{693332}$.
\item Types are not a separate syntax: a type is an ordinary term, passed to an opcode as an operand: $\str{add}\ \{\str{i32}, a, b\}$ is LLVM's
  $\kw{add\ i32}\ a, b$.
\item A struct's fields are ordered; a label may be empty (no label); the other labels are unique. A struct is
  consumed by projection, by opcodes, and
  by a byte array: applied to one, it selects a field (1/15, 1/17).
\item A byte array applied to a struct, $b\ \{l_1 = t_1, \dots, l_n = t_n\}$, is an
  opcode call: $b$ names the opcode and the struct holds its operands, as in
  $\str{add}\ \{\str{i32}, a, b\}$. $\fn{op}(b)$ is a partial function from
  operand values to a byte array. It is
  undefined for an effect, for undefined behavior (division by zero) and for an opcode it doesn't know, so
  reduction cannot reduce such a call. Effects include printing and every
  memory opcode: $\str{alloca}$, $\str{load}$ and $\str{store}$. Reduction has no
  memory: it never computes an address or the contents of one; the program orders
  memory opcodes with strict applications or by using one's result in the next (4/2).
\item Positions count every field, labeled or not, from $0$; a label is a
  name for one position. A struct applied to a byte array $b$ selects the
  field at position $b$; past the last field it selects the last one, so the
  last field is a default arm. In $s = \{x = a, b, y = c\}$: $s\ \hex{00} = s.x = a$, $s\ \hex{01} = b$,
  $s\ \hex{02} = s.y = c$. An unlabeled field is reached only by its position.
   With a constant byte array, both become LLVM's $\kw{extractvalue}$ with a constant index.
\item A struct is a value only when all its fields are values. Its fields are computed
  in no particular order: full $\beta$ may step any of them.
\item A branch is a struct applied to a byte array known only at
  run time: $\{\mathit{false} = t_2, \mathit{true} = t_1\}\ c$ takes $t_1$ when
  $c$ is not $0$ and $t_2$ when it is $0$, as LLVM's $\kw{br\ i1}$. With more
  fields it is a multi-way branch, as LLVM's $\kw{switch}$. The labels only
  document the arms.
\item A strict application $t_1\ {!}t_2$ applies $t_1$ to $t_2$ only once the argument is a
  value: $(\lam{x}{t})\ {!}y$ waits, while $(\lam{x}{t})\ y$ reduces to
  $\subst{x}{y}{t}$. It is the only way to order effects and to use one result
  more than once: $(\lam{c}{f\ c\ c})\ {!}e$ runs $e$ once, then the body; with
  $\lam{\_}{t}$ it only orders. The $!$ does not change grouping: it
  marks the argument as it is without $!$. So $f\ {!}x\ y$ is $(f\ {!}x)\ y$, and a compound
  argument needs parentheses: $f\ {!}(g\ y)$. The $!$ is not a term on its own.
\item Sugar: $\kw{let}\ x = t_1\ \kw{in}\ t_2$ is $(\lam{x}{t_2})\ t_1$, and
  $\kw{let}\ x \mathrel{=!} t_1\ \kw{in}\ t_2$ is $(\lam{x}{t_2})\ {!}(t_1)$. Here
  $=!$ is one sign: the strictness belongs to the binding, so $t_1$ extends to
  $\kw{in}$ as in a plain $\kw{let}$. So $\kw{let}$ may
  copy $t_1$ to every use of $x$ or drop it; $\kw{let}\ x \mathrel{=!} t_1$ runs $t_1$ once, first.
\item Sugar: $\kw{if}\ c\ \kw{then}\ t_1\ \kw{else}\ t_2$ is $\{t_2, t_1\}\ c$.
\item Terms are equal up to $\alpha$-equivalence (renaming bound variables).
  When a bound variable of $t_1$ clashes with a free variable of $t_2$,
  $\subst{x}{t_2}{t_1}$ first renames it ($\alpha$-conversion), then
  substitutes.
\item A stuck term is one no rule will ever reduce: a struct
  applied to a value that is not a byte array, the empty struct applied to anything, a byte array applied to a value that is not a struct, an opcode call
  whose operand is a value that is not data (a lambda somewhere in it),
   $v.l$ where $v$ is
  a lambda, a byte array or a struct with no field $l$. A program whose normal form contains a stuck term, anywhere, is rejected at compile time. An unknown opcode or undefined behavior is not stuck: it is a run-time operation (1/14).
\item A term is neutral when no rule reduces it yet: it waits for a free variable or for a run-time operation. Once its binder is applied it may reduce.
\end{points}

\section{Computation (at the root)}\label{sec:computation}

\begin{rules}
\axiomrow{E-Beta}
  {(\lam{x}{t_1})\ t_2 \;\step\; \subst{x}{t_2}{t_1}}
\rulerow{E-Proj}
  {l_i = l}
  {\{l_1 = t_1, \dots, l_n = t_n\}.l \;\step\; t_i}
\rulerow{E-Index}
  {b < n}
  {\{l_1 = t_1, \dots, l_n = t_n\}\ b \;\step\; t_{b+1}}
\rulerow{E-Default}
  {1 \le n \le b}
  {\{l_1 = t_1, \dots, l_n = t_n\}\ b \;\step\; t_n}
\rulerow{E-Opcode}
  {\fn{op}(b)(d_1, \dots, d_n) = b'}
  {b\ \{l_1 = d_1, \dots, l_n = d_n\} \;\step\; b'}
\axiomrow{E-Strict}
  {t\ {!}v \;\step\; t\ v}
\end{rules}
\begin{points}
\item A value is $\lam{x}{t}$, a struct or a byte array (Section~\ref{sec:syntax}).
\item \rn{E-Proj} takes the field labeled $l$ (labels are unique), and \rn{E-Index} the field at
  position $b$~(\rn{E-Default} the last field); the other fields are discarded, even one with an effect:
  $\{a = e, b = \hex{01}\}.b \step \hex{01}$ never runs $e$. To run it, bind it
  first with a strict application: $(\lam{x}{\{a = x, b = \hex{01}\}.b})\ {!}e$.
\item So a branch whose condition is known at compile time
  keeps one arm and discards the others; a discarded arm never runs.
\item \rn{E-Opcode} computes the call at compile time: all operands are
  data: byte arrays, or structs of data (row 9), never a lambda, so they never step and the result is the same in every
  reduction order, and $\fn{op}(b)$ is defined, so
  $\str{add}\ \{\str{i32}, \hex{02000000}, \hex{03000000}\} \step \hex{05000000}$.
  Otherwise reduction cannot reduce the call: it is a run-time operation (neutral): an
  effect, undefined behavior, or an operand not known until run time. The
  translation to LLVM emits it as an instruction. Operands are computed by
  \rn{E-App2} and \rn{E-Struct}.
\item \rn{E-Strict} fires only on a value: a value has no effect left to run.
  A strict application whose argument is a run-time operation waits; the translation to LLVM emits the operation
  first, then the rest, with the result as an SSA value. The argument is computed by
  \rn{E-SApp2}.
\end{points}

\section{Full \texorpdfstring{$\beta$}{beta}}\label{sec:congruence}

\begin{rules}
\rulerow{E-Abs}{t \step t'}{\lam{x}{t} \;\step\; \lam{x}{t'}}
\rulerow{E-App1}{t_1 \step t_1'}{t_1\ t_2 \;\step\; t_1'\ t_2}
\rulerow{E-App2}{t_2 \step t_2'}{t_1\ t_2 \;\step\; t_1\ t_2'}
\rulerow{E-Struct}{t_i \step t_i'}
  {\{\dots, l_i = t_i, \dots\} \;\step\; \{\dots, l_i = t_i', \dots\}}
\rulerow{E-Proj1}{t \step t'}{t.l \;\step\; t'.l}
\rulerow{E-SApp1}{t_1 \step t_1'}{t_1\ {!}t_2 \;\step\; t_1'\ {!}t_2}
\rulerow{E-SApp2}{t_2 \step t_2'}{t_1\ {!}t_2 \;\step\; t_1\ {!}t_2'}
\end{rules}
\begin{points}
\item $\step$ is full $\beta$: a rule of Section~\ref{sec:computation} may fire
  anywhere, under a lambda, in a struct field (so in every arm of a branch) too.
\item $\step$ is confluent: it is the $\lambda$-calculus with
   structs, projection, branching and
  strict application (Church--Rosser; projection is the usual record rule). The
  proof is in Lean 4, in \texttt{proofs/} (theorem \texttt{Oymomo.confluence}), for
  every opcode table $\fn{op}$.
\end{points}

%% ── Meaning ────────────────────────────────────────────────────────────

\section{What Runs}\label{sec:runs}

\begin{points}
\item Reduction never runs an effect: an effectful operation (an opcode call reduction cannot reduce, 2/10) is neutral at compile time. Full $\beta$ may copy or discard a term
  freely; since it is confluent, every order reaches the same normal form.
\item The program that runs is the normal form. Count the effects in it: each
  one runs exactly once. For example, with $p = \kw{print}\ \str{h}$ (an effect):
  \begin{itemize}[nosep]
  \item $(\lam{x}{\{x, x\}})\ p$ has the normal form $\{p, p\}$: $\str{h}$ is
    printed twice, because the program wrote $x$ twice;
  \item $(\lam{x}{\{x, x\}})\ {!}p$ waits for $p$: $\str{h}$ is printed once, and
    both fields hold its result.
  \end{itemize}
  Effects run in the order the program asks for, with a strict application or by using
  one effect's result in another; any other order is free.
\item So the translation to LLVM must keep every effect of the normal form, but may merge
  equal pure operations. For example, with $p = \kw{print}\ \str{h}$ and
  $q = \kw{add}\ \{\str{i32}, a, b\}$ (pure):
  \begin{itemize}[nosep]
  \item $\{p, p\}$ becomes two $\kw{print}$ instructions, never one;
  \item $\{q, q\}$ may become one $\kw{add}$ instruction whose result fills both
    fields;
  \item $(\lam{x}{\{x, x\}})\ {!}p$ becomes one $\kw{print}$ instruction whose
    result fills both fields.
  \end{itemize}
\end{points}

\section{Modules}\label{sec:modules}

\begin{points}
\item A module is $\lam{m}{\{l_1 = t_1, \dots, l_n = t_n\}}$: a struct of labeled
  definitions, declarations, constants and global variables. Each label is a global name, as LLVM's
  $\kw{@gcd}$ or $\kw{@puts}$. They refer to each other through $m$.
\item A definition is a struct
  $\{\mathit{result\_type} = t',\
  \mathit{body} = \lam{f}{\{\mathit{entry} = t_e, l_2 = t_2', \dots\}}\}$.
  $\mathit{result\_type}$ gives the result type; types are ordinary terms (1/12). The
  parameters and their types are those of the $\mathit{entry}$ block. $\mathit{body}$ is a recursive
  function: $f$ names its own struct of blocks. It becomes LLVM's
  $\kw{define}$.
\item A block is a struct $\{\mathit{param\_type} = \{x_1 = t_1, \dots, x_n = t_n\},\
  \mathit{body} = \lam{p}{t}\}$. $\mathit{param\_type}$ declares the
  types of the block parameters (LLVM's $\kw{phi}$). $\mathit{body}$ takes one
  argument, a struct of the same form as $\mathit{param\_type}$:
  $\{x_1 = t_1', \dots, x_n = t_n'\}$; $t$ reads it as $p.x_i$. The $\mathit{entry}$ block
  runs first. A jump is
  $f.l.\mathit{body}\ \{x_1 = t_1', \dots, x_n = t_n'\}$, LLVM's $\kw{br}$. A block sees only its own
  argument, $f$ and $m$.
\item A declaration is a struct $\{\mathit{param\_type} = \{x_1 = t_1, \dots, x_n = t_n\},\ \mathit{result\_type} = t'\}$,
  a function defined outside the module; $\mathit{param\_type}$ gives the parameter
  types in order: $\{\mathit{param\_type} = \{s = \str{ptr}\},\ \mathit{result\_type} = \str{i32}\}$
  becomes LLVM's $\kw{declare\ i32\ @puts(ptr)}$.
\item A constant is a struct $\{\mathit{type} = t_1,\ \mathit{value} = v\}$:
  $\{\mathit{type} = \str{i32},\ \mathit{value} = \hex{2a000000}\}$ becomes LLVM's
  $\kw{@answer\ =\ constant\ i32\ 42}$. $m.l$ stands for the value $v$.
\item A global variable is a struct $\{\mathit{type} = t_1,\ \mathit{init} = v\}$:
  $\{\mathit{type} = \str{i32},\ \mathit{init} = \hex{29000000}\}$ becomes LLVM's
  $\kw{@counter\ =\ global\ i32\ 41}$. $m.l$ stands for its address, a
  $\str{ptr}$; the program reads and writes it with $\str{load}$ and
  $\str{store}$.
\item $m.l$ stands for the function $l$ itself, so a call is a plain
  application to one struct: $m.l\ \{x_1 = t_1', \dots, x_n = t_n'\}$, LLVM's $\kw{call}$. For a definition, $m.l$
  is the $\mathit{body}$ of its $\mathit{entry}$ block with $f$ tied to its own
  struct of blocks.
\item $m$ and $f$ stay free variables, so calls and jumps are neutral: reduction
  never unfolds them, and a recursive function or a loop doesn't make
  reduction loop. The user may replace them (with a fixed-point combinator) to
  compute calls at compile time; a call to a declaration stays stuck: it has
  no $\mathit{body}$.
\item For example, Euclid's $\gcd$:
  \[
  \begin{array}{l}
  m \to \{\mathit{gcd} = \{\mathit{result\_type} = \str{i32},\ \mathit{body} = f \to \{\\
  \quad \mathit{entry} = \{\mathit{param\_type} = \{a = \str{i32}, b = \str{i32}\},\ \mathit{body} = \lam{p}{f.\mathit{loop}.\mathit{body}\ \{a = p.a, b = p.b\}}\},\\
  \quad \mathit{loop} = \{\mathit{param\_type} = \{a = \str{i32}, b = \str{i32}\},\ \mathit{body} = p \to\\
  \qquad \{\mathit{false} = f.\mathit{step}.\mathit{body}\ \{a = p.a, b = p.b\},\ \mathit{true} = f.\mathit{done}.\mathit{body}\ \{a = p.a\}\}\\
  \qquad (\str{icmp\_eq}\ \{\str{i32}, p.b, \hex{00000000}\})\},\\
  \quad \mathit{step} = \{\mathit{param\_type} = \{a = \str{i32}, b = \str{i32}\},\ \mathit{body} = p \to\\
  \qquad f.\mathit{loop}.\mathit{body}\ \{a = p.b, b = \str{urem}\ \{\str{i32}, p.a, p.b\}\}\},\\
  \quad \mathit{done} = \{\mathit{param\_type} = \{a = \str{i32}\},\ \mathit{body} = \lam{p}{p.a}\}\}\},\\
  \ \ \mathit{main} = \{\mathit{result\_type} = \str{i32},\ \mathit{body} = f \to \{\mathit{entry} = \{\mathit{param\_type} = \{\},\\
  \quad \mathit{body} = \lam{p}{m.\mathit{gcd}\ \{a = \hex{30000000}, b = \hex{12000000}\}}\}\}\}\}
  \end{array}
  \]
\end{points}
